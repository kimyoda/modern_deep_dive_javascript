## 44.2 REST API 설계 원칙

1. **URI는 자원을 식별** `GET /getTodos/1`이나 `GET /todos/show/1`보다 `GET /todos/1`처럼 대상을 드러냄
2. **HTTP 메서드에 맞는 동작을 요청** `GET /todos/delete/1` 대신 `DELETE /todos/1`을 사용. `GET`은 조회 목적의 안전한 메서드

| 메서드 | URI        | 동작                            | 요청 본문     | 성공 응답    |
| ------ | ---------- | ------------------------------- | ------------- | ------------ |
| GET    | `/todos`   | 목록 조회                       | 없음          | 200          |
| GET    | `/todos/1` | 단건 조회                       | 없음          | 200          |
| POST   | `/todos`   | 새 항목 생성                    | 생성할 데이터 | 201          |
| PUT    | `/todos/4` | 대상 변경 가능한 필드 전체 교체 | 전체 표현     | 200 또는 204 |
| PACTH  | `/todos/4` | 대상 일부 수정                  | 변경 데이터   | 200 또는 204 |
| DELETE | `/todos/4` | 대상 삭제                       | 없음          | 200 또는 204 |

POST는 HTTP에서 생성 전용은 아니나, API에서 컬렉션에 항목을 추가하는 의미로 사용. PUT은 서버가 허용하는 경우 지정 URI에 새 자원을 만들 수 있고 그때는 201을 반환할 수 있음. PATCH 본문 형식은 API 계약에 따른다
JSON server가 받는 필드 부분 수정 객체를 보냄

**멱등성**은 동일한 요청을 반복했을 때 서버에 의도된 효과가 한 번 호출했을 때와 같은 성질. GET·PUT·DELETE는 HTTP 의미상 멱등. 첫 DELETE가 204, 다음 DELETE가 404여도 삭제된 상태는 같을 수 있음. POST·PATCH는 메서드 자체만으로 멱등성이 보장되지 않음

| 상태                       | 내용                                                  |
| -------------------------- | ----------------------------------------------------- |
| 200 oK                     | 요청 성공, 결과 본문이 옴                             |
| 201 Created                | 생성 성공, `Location`이 있으면 생성된 자원 URI를 확인 |
| 204 No Content             | 성공했지만 본문이 없음. JSON 파싱을 건너뜀            |
| 400 Bad Request            | 요청 형식이나 값이 잘못되었는지 확인                  |
| 404 Not Found              | 경로 또는 자원 ID를 확인                              |
| 415 Unsupported Media Type | 요청 성공, 결과 본문이 옴                             |
